# Zero-padding in the `mismatched` audit arm: what the existing data show

Generated by `scripts/analyze_mismatched_padding.py` (CPU only; reads `results/`, writes nothing there).
Runs: the three v9 primary runs (`20261009_113254` Qwen2.5, `20261011_141020` Mistral, `20261011_221317` Qwen3-8B)
and the four donor-draw reruns (`20261011_150444`, `_184238` Qwen2.5; `20261011_234807`, `20261012_093630` Mistral).
n=100 scored questions each, 2 substituted hops per question (agent_idx 1 and 2).

## Answer in four points

1. **EXACT: 100% of mismatched substitutions were length-adjusted.** `shape_resized` is true on all 200 hop-substitutions in every one of the 7 runs. No donor ever matched the target length, so every mismatched cache was either truncated or zero-padded.
2. **EXACT bounds:** at least 18-29% of substitutions were *certainly* zero-padded (target longer than even a donor that generated the 512-token cap) and at least 29-42% were *certainly* truncated. The remaining ~30-50% cannot be classified without the donor's generated length.
3. **ESTIMATE:** with the donor's generated length set to the median of the scored questions in the same run, about **half (49-61%) were zero-padded and half truncated**. The zero tail averaged **roughly 9-13% of the injected cache's positions across all substitutions** (about 5-15% over the plausible range of donor lengths). That mean includes the truncated substitutions, which have no padding.
4. **Reading:** padding is common but moderate, and the other half of substitutions lose the donor's tail instead. The mismatched drop (29.0% vs 59.0% dropped on Qwen2.5) is therefore not obviously a padding artifact, but this analysis cannot exclude a contribution; the data do not let padding be separated from content mismatch. A clean test needs the new per-sample log (exact lengths, see `lakv/causal_audit.py::describe_seq_len_handling`) on a rerun, or a matched-length donor control.

## What is exact and what is estimated

* **Exact**: `shape_resized`; target cache length per hop, from `hop_stats[hop].original_mb * 1e6 / bytes_per_position` (28 layers x 2 x 4 kv heads x 128 x 2 B = 57,344 B/position for Qwen2.5; 131,072 for Mistral; 147,456 for Qwen3-8B). All 1,400 cache sizes were integer multiples of that, which supports the formula. Hop 0 is never injected, so it is the exact target for the agent_idx=1 substitution; hop 1's cache as produced in that run is the target for agent_idx=2.
* **Exact**: donor *prompt* length (the donor question text is logged; tokenized with the model's own tokenizer, the pipeline's chat template and the per-agent system prompt).
* **Not stored anywhere**: the donor's generated length (and its Verifier-hop length for agent_idx=2). **Estimate** = median generated length of the scored questions in the same run (computed exactly per scored question as `gen0 = L0 - P0`, `gen1 = L1 - L0 - P1`). Hard bounds use 0..512 tokens per hop; "plausible" uses the 5th-95th percentile of observed generation lengths.
* **Not done**: relating padding to per-sample correctness. With estimated lengths that would be an estimate stacked on an estimate; the new instrumentation is the right way to do it.

## Caveats

* The Verifier hop hits the 512-token cap in more than 5% of questions (p95 = 511), which widens the agent_idx=2 bounds.
* Cache lengths can be off by one token (the last generated token is not always forwarded). That does not change any percentage here.
* Mistral and Qwen3-8B tokenizers were downloaded for this analysis (tokenizer files only). Qwen3's `tokenizer.json` does not load in the installed `tokenizers` version, so the slow tokenizer was used; it gives the same token ids.
